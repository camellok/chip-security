# DCSM 勘误与验证记录（待确认）

本文件记录 DCSM 培训例程验证中观察到的行为，以及应用调用、驱动、工具和文档之间待确认的差异。条目编号用于跟踪验证，不代表已确认芯片或驱动存在缺陷。

## DCSM-001：当前调用流程在 FORCESEC 后未能再次解锁 Zone1

记录日期：2026-10-21。

状态：现象已复现；补充 OTP/ZSB 读取的库内试验及随后迁移到应用层的版本，均已由开发者确认板级验证通过。当前例程保持驱动库原样。根因尚未确认，仍可能与应用用法、初始化前置条件、访问时序或平台实现有关，不能据此归责于驱动库或芯片。

TI F280025C 是否存在同类现象尚未验证，由开发者另行确认。本条目不将昊芯板级结果推广到 TI，也不预设任何驱动版本会因本条目而变更。

版本说明：以下板级现象和 10 轮验收记录来自原 SPWM / Z1 首个 ZSB 版本。当前 ex00～ex02 已调整为产品模块，ex01/ex02 使用代码与参数分区及 Z1 ZSB2；其新版板级结果单独记录在 [简要回归表](../validation/hx28002x/REGRESSION_EX00_EX02.md)，不沿用历史验收结论。

| 项目 | 本次验证环境 |
| --- | --- |
| 目标器件 | 当前 HX280025 / DSC28002x 演示板；具体芯片修订号未记录 |
| IDE | Haawking IDE 2.3.17 |

当前结论仅覆盖上述验证环境，尚未验证 Zone2、其他 ZSB、其他芯片修订或其他驱动版本。

### 问题现象与复现步骤

1. 使用原始解锁流程：计算 ZSB 地址，读取四个 CSMPSWD 字，再写入四个 CSMKEY 寄存器。
2. 连接仿真器，调试启动流程已使 Zone1 解锁，`Z1_CR=0x60`。
3. 第一次按键调用 `DCSM_secureZone1()`，通过 FORCESEC 重新锁定。调用返回后观察到 `Z1_CR=0x08`。
4. 第二次按键调用 `DCSM_unlockZone1CSM()`。四次密码读取后、第一次 KEY 写入前，`zsbBase=0x007A0040`，但 `Z1_CR=0x00`。
5. 写完 KEY 后仍无法解锁。后续重复按键，观察到 `Z1_CR` 一直为 `0x00`。

此外，独立上电后的首次软件解锁已在前序实验中成功；故障出现在 FORCESEC 后的再次解锁路径。

### 定位证据

以下均为 32 位寄存器的字节地址。`Z1_CR=0x00039430`，bit6 ARMED 掩码为 `0x40`，bit5 UNSECURE 掩码为 `0x20`，bit3 ALLZERO 掩码为 `0x08`。

| 对照操作 | 实测结果 | 能支持的结论 |
| --- | --- | --- |
| 反汇编检查原解锁函数 | 四次密码读取和四次 KEY 写入均存在，访问宽度为 32 位 | 不是读取被编译器省略 |
| 失败现场通过 `monitor mdw 0x007A0050 4` 读取密码地址 | 返回四个零；随后 `Z1_CR` 仍为 `0x00` | 直接用调试器读取这四个地址也未恢复 ARMED |
| 在失败现场执行 `monitor hxs320f280025c_edd unlock 0`，随后读 Z1_CR | `Z1_CR=0x60` | 工具解锁路径在同一现场有效 |
| 补充下述 Zone1 OTP/ZSB 读取后再测试 | 开发者确认板级有效 | 这组补充步骤可作为当前环境的临时规避依据 |

密码区读回零不等于 OTP 中的密码被改成了零；ARMED 未置位时，也不能只凭 ALLZERO 的状态认定密码永久全零或 OTP 损坏。

### 工具与驱动的流程差异

TRM §3.12.7.2 描述的基本 PMF 为四次密码读取，再四次 KEY 写入。当前调用的驱动 API 包含这些操作；应用是否还应满足其他初始化或时序条件，尚待确认。

对本机 `D:/Haawking-IDE-2.3.17/haawking-tools/openocd/bin/openocd.exe` 的带符号反汇编检查发现，`hxs320f280025c_edb_unlock` 在密码读取前还执行 OTP 头部及选中 ZSB 配置读取。该函数中未见复位调用；此结论不等同于已审计整个命令调用链。

用于比对的工具 SHA-256：`6AD15CE6383A8193A48E0A9C1FB55DDC8C6C0F4833449F82FEF97E11113AAC02`。

原工具同时处理 Zone1、Zone2；本次试验仅提取对应的 Zone1 读取步骤，未完整复制工具的跨 Zone 流程。

### 已验证的临时规避步骤

保持原有 KEY 内容、32 位访问宽度和 ZSB 选择算法不变，在原密码读取前增加以下步骤。所有新增操作均为 volatile 读取，不写 OTP。

| 顺序 | 读取字段 | Zone1 地址 |
| --- | --- | --- |
| 1～3 | OTP LINKPOINTER1、2、3 | `0x007A0000`、`0x007A0008`、`0x007A0010` |
| 4 | PSWDLOCK | `0x007A0020` |
| 5 | CRCLOCK | `0x007A0028` |
| 6 | BOOTPIN_CONFIG / GPREG1 | `0x007A0018` |
| 7 | GPREG2 | `0x007A001C` |
| 8～9 | BOOTDEF_LOW / GPREG3、BOOTDEF_HIGH / BOOTCTRL | `0x007A0038`、`0x007A003C` |

随后读取运行时 LINKPOINTER、计算当前 ZSB，再依次读取 ZSB 的 EXEONLYRAM、EXEONLYSECT、GRABRAM、GRABSECT 四个配置字，偏移分别为 `+0x00/+0x04/+0x08/+0x0C`。最后执行原有的四次密码读取和四次 KEY 写入。

本次没有逐项删除读取后再复测，不能认定表中每个字段都必须读取，也不能断言任何一个单独字段就是根因。目前只能确认这组补充读取在已测环境中有效；它可能补充了当前应用尚未满足的使用前提，也可能涉及其他时序或平台条件，确切机制仍待确认。

### 驱动库与例程的处理原则

培训例程应保持驱动库原样，应用层的试验步骤应单独标识并记录适用条件。后续应先确认推荐用法、必要前置条件和访问时序，再根据实测结果决定例程如何调整。

首次记录时，ex02 中为定位现象加入的 `dcsm.c` 试验改动仍保留。随后已将这部分试验改动撤回；当前 ex02 的 `dcsm.c` 已恢复，并通过 SHA-256 比对确认与 ex01 文件完全一致。原库内试验仅用于对照，不直接回填到 ex01 或其他例程。

当前 ex02 已在 `src/main.c` 添加私有函数 `Prepare_Zone1_Unlock()`，承担前述 OTP 头部和 ZSB 配置读取，随后仍调用原始 DriverLib API：

```c
Prepare_Zone1_Unlock();
DCSM_unlockZone1CSM(&s_z1_demo_key);
```

准备函数按运行时 LINKPOINTER 计算 ZSB，未写死为首个 ZSB，未增加全局变量，也未写 OTP。DriverLib 仍负责密码读取和 KEY 写入；相较已验证的库内试验，调用原始 API 时会再次读取运行时 LINKPOINTER 并计算 ZSB。准备函数位于普通 APP Flash；后续是否保留或调整，应以用法确认和板级回归结果为依据。

应用层版本已通过构建、map 和反汇编检查。2026-10-21，开发者确认迁移后的应用层版本板级验证通过；此结论独立于此前库内试验的结果。补充反馈如下：

- 独立上电为 secure，LED 正常闪烁。
- 连续 10 轮锁定/解锁均成功；锁定后 `Z1_CR=0x00`，解锁后 `Z1_CR=0x60`。
- 锁定后直接读取 `0x00610000` 返回全零，调试连接保持；解锁后读数恢复正常。
- 解锁时 LiveView 能观察正弦表、idx 递增和 cmp 变化；锁定时表读数全零，idx、cmp 保持先前值。后两者位于非安全 RAM，停止变化对应例程主动暂停算法调用，不能作为 RAM 读保护证据。
- 解锁后断电重启恢复 secure。

当前 ex02 演示目标已验收通过。此结果不确定补充读取的根因或最小必要序列，也不扩展到未测平台、Zone 或 ZSB。

## DCSM-002：280013x ex02 FORCESEC 后再次解锁失败

2026-10-24 开发者反馈 280013x ex02 按键锁定后无法再次解锁，尚未提供失败现场 CR 或逐阶段日志。该现象与 DCSM-001 的 28002x 记录相似，但根因和平台等价性未确认；ex01 此前的板级通过结论保持。

开发者要求参照 28002x 应用层方案适配。280013x ex02 现新增私有 `Prepare_Zone1_Unlock()`，在原始 `DCSM_unlockZone1CSM()` 前执行，只进行 volatile 读取，不写 OTP，不修改厂商驱动：

1. Zone1 OTP 依次读取 LINKPOINTER1/2/3、JLM_ENABLE、GPREG1/2/3/4、PSWDLOCK、CRCLOCK、JTAGPSWDH0/1。CRCLOCK 采用 TRM 所列+0x24，SDK 未提供该偏移宏。
2. 读取运行时 Zone1 LINKPOINTER，扫描 bit13 至 bit0；全 1 选择 OTP_BASE+0x40，否则与本平台 DriverLib 相同，按 OTP_BASE+(bitPos+2)*0x40 计算活动 ZSB。
3. 按 280013x 布局读取活动 ZSB 的 GRABSECT1/2/3（+0x10/+0x14/+0x18）、GRABRAM1（+0x1C）、EXEONLYSECT1/2（+0x28/+0x2C）、EXEONLYRAM1（+0x30）、JTAGPSWDL0/1（+0x38/+0x3C），跳过保留位置。GRABSECT3+0x18 沿用已接受的实验定义；EXEONLYSECT2+0x2C 仍为推定布局，本次仅读取，不启用该字段的 OTP 输出。
4. 原始 DriverLib 继续完成四次密码虚读和四次 KEY 写入。

TRM V1.3 安全初始化说明列出了两 Zone 的头部及 ZSB 配置虚读，并说明完整安全初始化由 BootROM 执行、顺序重要。此函数仅提取 Zone1 作为应用解锁前的试验准备，未实现两 Zone 完整 BootROM 初始化，也不将所有读取认定为最小必要序列。

构建通过。反汇编确认函数位于普通 APP Flash（本次 0x00600852），12 次头部读取、1 次运行时 LINKPOINTER 读取和 9 次 ZSB 配置读取均为真实 32 位 lw；原始驱动中的四次密码读取和 KEY 写入保留。厂商 dcsm.c 的 SHA256 前后均为 9C63CB9850D8A3488C71A7154D2F0B0F8FC18DE882B7833A018A390DDA2C1EA4。当前 OTP 源仍由开发者 Exclude，本轮应用 HEX 为 22706 字节，ELF 及两份 HEX 无 OTP。未连接硬件，规避效果待板级复测。

复测顺序：仅更新应用 Flash；断电启动后按键解锁，再锁定、再次解锁。记录各次 CR>>16 与计算恢复情况，先完成 3 轮，再累计 10 轮，并确认断电后恢复 secure。调试期间关闭 OTP 自动刷新窗口，避免额外读取干扰初始化顺序。


2026-10-24 板级复测反馈：开发者确认“这样子可行，我认为ex02通过”。应用层准备读取方案在当前 280013x ex02 获得板级通过反馈；未补报具体循环次数或寄存器值。该反馈不确认最小必要序列或芯片/驱动根因，不扩展到其他 Zone 和槽位。
