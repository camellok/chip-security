# DCSM 项目 FAQ

本文件适用于本项目的基础系统和 DCSM 例程。接线、演示密码和实验步骤见各例程 README；这里集中说明配置原理、常见现象和排查方法。地址示例使用昊芯 DSC28002x 工程的字节地址。

## FAQ-001：串口没有任何数据，是否被 DCSM 限制了？

先确认程序是否执行到发送位置，以及串口通路是否完整。检查 TX/RX 交叉连接、共地、端口号、波特率和引脚复用，并按原理图核对跳线、串联电阻及连接器。板上未焊接的 0 Ω 电阻也会让串口通路断开。

先打开终端再复位，避免漏掉仅在启动时发送一次的日志。可用示波器或逻辑分析仪观察 MCU 的 TX 引脚：引脚已有波形而 PC 收不到时，优先检查板级通路和适配器。

若程序在串口初始化前停住，再检查启动流程、时钟、RAM 初始化和安全区访问。不能仅凭没有日志就判断是 DCSM 问题。

## FAQ-002：为什么连接调试器能运行，独立上电却不运行？

调试器可能执行了复位、加载 RAM 或密码解锁，使调试环境与独立启动不同。检查启动模式、Flash 入口、进入 main 前的初始化，以及调试配置中的自动解锁动作。

需要搬到 RAM 的数据和代码，应同时核对运行地址与 Flash 加载地址。若普通 APP 中的启动代码需要从尚未解锁的安全 Flash 读取初始化镜像，访问权限可能不满足。

可依次在启动入口、初始化函数、main 和外设初始化后定位停点；修正后应通过断电重上电复测。

## FAQ-003：变量的加载地址和运行地址有什么区别？

加载地址表示初始镜像存放在哪里；运行地址表示 CPU 执行代码或访问变量时使用哪里。初始化数据可以保存在 Flash，启动时复制到 RAM，之后通过 RAM 地址读写。

有初值的可写变量通常放在 RAM 数据段，零初始化变量通常放在 BSS，由启动代码清零。把一个会自增的变量直接放到 Flash 运行地址，普通赋值无法完成它所需的更新。

RAM 运行函数也有同样的区别。调整安全区时，要检查链接 map 中的 load address，并核对启动复制的源地址、目标地址和长度。

## FAQ-004：为什么有些函数必须在 RAM 中运行？

函数执行要求由器件和所执行的操作决定。例如本项目的器件初始化要求 Flash 等待周期配置函数在 RAM 中运行。Flash 擦写期间的执行位置也需要遵守器件和 Flash API 的约束。

DCSM 配置不会替代这些要求。可以把函数的加载镜像放在启动代码可读的普通 Flash 中，启动时复制到 RAM，再从 RAM 调用。

## FAQ-005：安全区中的算法能运行，为什么索引和输出仍然可见？

内存保护以 RAM 块、Flash sector 等资源为单位。算法函数和常量表放在安全 Flash，不会让其写入非安全 RAM 的计算结果自动受到保护。

观察到 RAM 中的索引和结果，只能说明这些 RAM 地址可访问。验证 Flash 读保护时，应直接检查受保护 Flash 的真实内容是否能被未授权读取。需要保护运行状态时，还应规划相应 RAM 的归属及数据输出方式。

## FAQ-006：LiveView 可以看到安全区内容，是否说明配置失效？

先确认读取发生时的安全状态。调试器可能在连接、下载或启动阶段完成了解锁；上电时输出的一条 secure 日志无法代表整个会话。

还要区分变量名、地址、ELF 中的符号信息、缓存显示和实际目标内存读数。对常量数组，固定观察同一个元素，并用 Memory 窗口读取其真实地址。

在 28002x 工程中，Z1_CR 地址为 `0x00039430`。`UNSECURE` 位掩码为 `0x20`，`ARMED` 为 `0x40`；当前驱动在 `(Z1_CR & 0x60) == 0x60` 时返回已解锁状态。

允许仿真执行和完全解锁安全内存也可能涉及不同的调试权限流程，具体以器件 TRM 和调试器行为为准。无法建立未解锁的调试会话时，可使用 downloader 做密码正确与错误时的回读对照。

## FAQ-007：资源仍显示属于 Zone1，为什么已经能读取？

资源归属和区域当前是否解锁是两个状态。解锁后，原先分配给 Zone1 的 sector 仍可保留其 Zone1 归属，访问权限则随当前安全状态变化。

排查时同时读取 GRAB 配置、区域控制寄存器和资源状态寄存器，不要用单个字段代替全部判断。以 sector4 为例：

| 项目 | 当前工程地址或字段 |
| --- | --- |
| Z1_GRABSECTR | `0x00039434`，sector4 为 `[9:8]` |
| Z2_GRABSECTR | `0x00039484`，sector4 为 `[9:8]` |
| B0_SECTSTAT | `0x000394A4`，sector4 为 `[9:8]` |
| Z1_CR | `0x00039430`，查看当前解锁状态 |

当前驱动将 SECTSTAT 的两位状态解释为：`00` 不可访问、`01` Zone1、`10` Zone2、`11` 完全访问。记录测试结果时应同时保存原始值和读取时机。

## FAQ-008：只使用 Zone1，为什么还要考虑 Zone2？

RAM 和 Flash 的归属由两个 Zone 的 GRAB 字段组合决定。在本项目采用的配置中：

| Zone1 字段 | Zone2 字段 | 资源归属 |
| --- | --- | --- |
| `01` | `10` | Zone1 |
| `10` | `01` | Zone2 |
| `10` | `10` | 非安全 |

因此，只启用 Zone1 的保护功能，也要核对 Zone2 对应字段。不参与构建的配置文件不会撤销芯片已有 OTP，更不能代表对应字段为零。

其他组合还有条件和限制，尤其 `11/11` 的可访问性与两个 Zone 的状态有关。不要把“不是 01”统一理解为非安全，也不要只根据一侧字段判断。

## FAQ-009：OTP 汇编文件和链接脚本分别负责什么？

汇编文件通过 section 和数据伪指令定义配置字及排列顺序；链接脚本给这些输入段指定实际地址，并通过 KEEP 等规则保留所需数据。

本项目按字段组输出 OTP 段。省略一个独立 section 中的数据，不应让其他已经单独定位的 section 移位。但同一 section 内的数据连续排列，删掉中间一个保留字，会改变后续字段的地址。

应按 TRM 的偏移核对最终 map 和 HEX。未输出的地址表示本次产物没有为其提供数据，并不代表芯片该处会被擦除、写零或自动恢复默认值。

## FAQ-010：源码里有配置，为什么 map 或 HEX 中没有？

检查该文件是否参与当前构建配置、是否生成目标文件，以及链接脚本中的输入段名称是否匹配。还需确认段是否被垃圾回收、是否使用了必要的 KEEP，以及段内是否真的输出了数据。

一个只有 section 声明、数据全部被注释的段可以是零大小。看到段名不等于看到配置数据。应核对段地址、大小和 HEX 的实际记录。

昊芯目标使用工程中的 RISC-V 汇编文件。目录里的 TI 参考 asm 不应被误当成实际编译输入。

## FAQ-011：三个 LINKPOINTER 要怎样配置？

三个 LINKPOINTER 是同一 Zone 的冗余配置副本。本项目为它们填写相同值，并检查器件解析后的 LINKPOINTER 及 LINKPOINTERERR。28002x 的指针字之间含保留字；280013x 的三个指针连续排列，不能复制同一份布局。

LINKPOINTER 是选择 ZSB 的编码，不能把 ZSB 地址直接填进去。28002x 中 `0x1FFFFFFF` 选择首个 ZSB；280013x 使用低 14 位的 `0x3FFF`。后续 ZSB 的选择应按对应芯片 TRM 的编码和地址规则核对。

TI C28x 资料与昊芯 RISC-V 工程可能采用不同的地址单位。图中偏移、ZSB 内字段偏移和 CPU 字节地址应分别核对，不能直接照抄另一个平台的数值。

## FAQ-012：为什么密码正确却仍然解锁失败？

核对目标 Zone、当前 LINKPOINTER 选择的 ZSB、四个密码字的顺序和每个字的数值。工具中的密码、固件中的软件密钥和已烧入 OTP 的有效密码需要对应。

OTP 中可能已有出厂编程位。写入值受到只能从 1 到 0 的限制，实际密码不能只根据源文件推断。应在首次编程前保存初值，并在允许读取时核对有效内容。

以 28002x ex01 为例，第二个密码字为 `0x02222222`，并非 `0x22222222`；280013x ex01 的第二字为 `0x00222222`。排查时还应保存工具错误信息和安全状态寄存器值。

## FAQ-013：回读得到全零，是否表示 Flash 被清空？

仅凭回读文件中的全零无法判断存储内容。它可能是受限读取的返回值，也可能是工具在读取失败后填入的占位数据；具体要结合工具日志确认。

每次断电重启后，分别使用错误密码和正确密码读取相同地址范围。比较安全区、非安全区及正确密码回读与构建产物的对应关系。若正确密码能读到原有算法内容，说明之前的全零不是实际内容被清空。

普通 Flash 回读和 USER OTP 回读可能受到不同保护规则影响，两个范围应分别记录。

## FAQ-014：怎样确认一个安全例程验证完成？

以例程目标为准，至少记录实际内存归属、独立运行现象、密码解锁结果、断电后的状态，以及未授权访问的结果。

保护 Flash 算法时，应同时确认应用在锁定状态下正常运行，错误密码无法取得真实算法内容，正确密码回读与构建产物一致。仅能进入 Debug、看到 LED 加快或得到一条解锁日志，都不能单独代替这些检查。

归档时保存工具版本、源码与构建产物、实际寄存器值、串口日志和回读结果。密码及 OTP 备份应按项目的访问管理要求保管。

## FAQ-015：演示密码和当前 OTP 模板能直接用于量产吗？

本项目的演示密码公开，且保存在非安全 APP 中，适合学习配置和解锁流程。量产前需要重新设计密码管理和更新方式，并审查密码位置保护、调试权限、启动配置及恢复流程。

PSWDLOCK 保护 OTP 中密码位置的可读性。保留密码可读的开发配置，意味着具备相应访问能力的人员可能取得密码；不能将一次错误密码回读失败当作完整的量产安全评估。

保留区和未使用 ZSB 的填零会消耗 OTP 的后续配置空间。本项目未把这类最终锁定操作作为基础实验步骤，不应直接取消模板中量产字段的注释。

## FAQ-016：进入 Debug 时 Flash 已擦除，随后报擦除错误怎么办？

2026-10-23，ex03 调试控制台先报告 `Target Unlocked` 和 Bank0 sector0～12 已擦除，随后报 `error code:-13`、`failed erasing sectors 32 to 32`、`flash_erase returned -4`。检查发现启动项仍启用完整 ELF 镜像下载，而 ELF 包含 USER OTP 数据。额外区域下载是本次重点排查项；日志不足以确定厂商错误码含义，工具 sector32 也不能直接视为芯片物理 sector32。错误根因和工具行为仍需完整日志或工具实现确认。

停止重复启动，保存日志并回读 USER OTP（`0x007A0000` 起、`0x800` 字节），确认指针和安全配置。程序 Flash 已被擦除，不能继续将无日志或不启动当作 DCSM 运行现象。确认配置后，使用 downloader 仅恢复程序 Flash，不写 OTP，再进行无下载调试。

ex03/ex04 的 launch 已改为无下载、关闭 Load image、保留符号加载。IDE 可能缓存旧配置，启动前须在实际使用的 Debug Configurations 中确认设置；仍可保留密码解锁用于调试，但它不应触发 OTP 编程。生成不含 OTP 的 HEX 只影响该 HEX，不会让另行加载的完整 ELF 自动排除 OTP。

本次后续回读确认 APP sector0～3 全部为 FF、入口已擦除，OTP 除预期的三个指针 FE→FC 外未变。只改无下载设置不会恢复程序，默认等待 main 的调试流程也无法到达已不存在的主程序，需先恢复程序 Flash。若恢复后仍在连接或初始化阶段失败，保存新的完整日志另行判断。sector4 读回零可能来自 execute-only 限制，不能按 APP 的全 FF 结论推断安全区也已擦除。

## FAQ-017：280013x 工程是否可以直接沿用 28002x 的配置？

不能直接沿用。平台统称为 280013x，当前具体工程目标为 2800137_EDE / PM 核心板；LED 为 GPIO20/22、SW2 默认 GPIO1，串口 GPIO28/29。安全模块代码/参数地址虽保持 `0x00610000` / `0x00614000`，实际属于扇区 32～39 / 40～47。DCSM 基址、CR 位位置、ZSB 步长和密码工厂位均不同。见[280013x平台说明](../examples/hx280013x/README.md)。

280013x 当前 ex01 的 ELF 和 `_dcsm.hex` 包含 APP 与 OTP，普通 HEX 仅含程序 Flash；ex02 保留 OTP 源 Exclude 设置，ELF 和两份 HEX 均无 OTP，已构建复验。launch 下载实际 ELF，可能自动解锁，下载前核对段范围，观察时检查实时寄存器。开发者反馈 ex00～ex02 板级通过，分项证据待补录；28002x 的读取实验和板级轮数不作为 280013x 结果。详见[当前进度](../../../docs/ROADMAP.md)及[双HEX说明](HX280013X_DUAL_HEX_BUILD.md)。
