# ex02：DCSM 调试观察

本例程基于 ex01，在相同的 Zone1 sector4 配置下演示软件锁定、解锁及调试可见性。ex01 保持不变。

## 最小演示逻辑

- SCIA：GPIO28 RX、GPIO29 TX，9600、8N1；LED：GPIO31；按键：GPIO9，低有效。
- LED 每 250 ms 翻转一次，与安全状态无关。按键至少保持 300 ms 后松开，触发一次操作；按住期间轮询程序等待松手，LED 暂停翻转。
- 当前已解锁时，按键调用 `DCSM_secureZone1()`；当前未解锁时，按键使用 ex01 演示密码调用 `DCSM_unlockZone1CSM()`。
- 操作前打印 `Request lock/unlock`，操作后打印实际 `secure/unlocked` 状态。如果操作后状态未变化，不能认定请求成功。
- 仅解锁时调用 SPWM。锁定时 CPU 留在普通 APP 中，便于观察调试访问。算法变量停止变化是程序主动暂停调用，不能视作读保护证据。
- 未增加全局状态变量。`g_sine_table_idx`、`g_epwm_cmp_value` 仍在非安全 RAM；正弦表和算法函数仍在 Zone1 sector4。

## 构建与下载

在 Haawking IDE 中导入 `ex02_dcsm_debug` 后刷新工程。已提供 `ex02_dcsm_debug.launch`，基于 ex01 调试配置，工程名与 ELF 路径已改为 ex02，可在 Debug Configurations 中选择。它保留了 ex01 的密码和自动解锁命令，因此连接后可能已经处于解锁状态；实验时需明确检查这些选项。

可使用已完成 ex01 配置的芯片，不需要新增 OTP 写入。保留的 Security 文件仍会向完整 HEX 输出 OTP 段，下载时选择仅更新 FLASH、保留 USER OTP。

## 演示步骤

1. 断电重启，不连接调试器。应打印 `Zone1 secure`，LED 闪烁，算法变量暂停更新。按键后应解锁，再次按键应重新锁定。
2. 连接调试器。如果启动时打印 `unlocked`，调试启动流程可能已自动解锁；观察当前寄存器，不依赖之前的串口日志。
3. 解锁时观察两个 RAM 变量更新，以及内容固定的正弦表。在 Memory 窗口直接读目标地址 `0x00610000`，首个 32 位数据应为 `0x3F000000`，即 `0.5f`。
4. 先关闭正弦表窗口的自动刷新，再按键锁定。核对串口结果和 `Z1_CR`，随后手动读取 sector4，记录读回结果。IDE 可能缓存常量或自动解锁，LiveView 显示本身不能证明读保护状态。
5. 如果调试连接保持，再按键解锁，算法变量恢复更新。若重新锁定造成仿真断连，记录为平台实测行为，采用分阶段连接验证，不预设昊芯与 TI 的 ECSL 行为完全一致。
6. 断电后再次确认恢复保护。无法进行未授权调试读取时，可沿用 ex01 的 downloader 正确/错误密码回读对照。

## FORCESEC 后再次解锁：已知问题与临时规避

在当前应用调用流程和已测昊芯板上，重新锁定后读取四个密码地址未使 ARMED 置位；实测此时 `Z1_CR=0x00`，而工具命令 `monitor hxs320f280025c_edd unlock 0` 可恢复至 `0x60`。根因尚未确认，可能涉及用法或初始化前置条件，不能据此认定驱动或芯片存在缺陷。TI F280025C 是否有同类现象由开发者另行验证。

对照本机 IDE 2.3.17 的 `openocd.exe` 中 `hxs320f280025c_edb_unlock` 符号，工具在写 KEY 前还读取 OTP 头部及选中 ZSB 的配置字段。当前 ex02 在 `main.c` 中通过私有函数 `Prepare_Zone1_Unlock()` 补充三个 OTP LINKPOINTER、PSWDLOCK、CRCLOCK、BOOTPIN_CONFIG、GPREG2、BOOTDEF_LOW/HIGH 和选中 ZSB 四个配置字的读取，然后调用原始 `DCSM_unlockZone1CSM()` 读取密码并写 KEY。准备函数按当前 LINKPOINTER 计算 ZSB，所有补充操作均为读取，不写 OTP，也不新增全局变量。

此前库内试验已由开发者确认板级有效，但尚未证明是最小必要序列；现已恢复驱动库，`dcsm.c` 经哈希比对与 ex01 一致。迁移后的应用层版本已通过构建、map 和反汇编检查，并于2026-10-21由开发者确认板级验证通过。根因及 TI F280025C 的对应行为仍待确认。工具原实现还包含 Zone2 的读取，本次仅处理 Zone1。详细复现、证据和处理原则见培训根目录的 [DCSM_ERRATA.md](../../DCSM_ERRATA.md)。

## 板级验收记录

2026-10-21，开发者在当前昊芯板、当前调试环境及应用层补充读取版本上反馈以下结果。ex02 的当前演示目标判定通过。

| 项目 | 实测结果 |
| --- | --- |
| 独立上电 | Zone1 为 secure，LED 正常闪烁 |
| 重复切换 | 共10轮锁定/解锁，每轮均成功 |
| 锁定状态 | `Z1_CR=0x00`，UNSECURE 为0，直接读取 `0x00610000` 返回全零，调试连接保持 |
| 解锁状态 | `Z1_CR=0x60`，正弦表读数正常，LiveView 可观察到 idx 递增、cmp 变化 |
| 锁定后的算法状态 | 正弦表读取返回全零；idx、cmp 保持锁定前的值 |
| 断电重启 | 恢复 secure |

锁定后正弦表的全零读数不表示其 Flash 内容被改写。idx、cmp 位于非安全 RAM；锁定时不再变化，是本例程主动暂停调用 SPWM 的结果，不是安全 RAM 读保护的证明。当前实测说明锁定安全内存与保持调试连接可以同时发生，但不据此推断工具的具体授权机制或其他平台行为。

应用层补充读取的根因和最小必要序列仍待确认；上述验收不预设驱动或芯片存在缺陷，也不包含 TI F280025C 的验证结论。

## 寄存器观察

以下为 32 位寄存器的字节地址。

| 寄存器 | 地址 | 检查内容 |
| --- | --- | --- |
| Z1_CR | `0x00039430` | bit6 ARMED、bit5 UNSECURE；按当前驱动，掩码 `0x60` 全部置位时为已解锁 |
| B0_Z1_GRABSECTR | `0x00039434` | sector4 的 `[9:8]` 应为 `01` |
| B0_Z2_GRABSECTR | `0x00039484` | sector4 的 `[9:8]` 应为 `10` |
| B0_SECTSTAT | `0x000394A4` | 记录 sector4 的 `[9:8]`，区域归属和解锁状态分别确认 |

变量地址以新 map 为准。锁定对照时将断点放在 `main.c` 的普通 APP 代码中，避免停在 sector4；`DCSM_secureZone1()` 为内联函数，实际位置需结合 main 的反汇编观察。

与 ex01 相同，演示密码明文保存在 APP 中。本例程用于解释访问控制，不用于量产密码配置。
